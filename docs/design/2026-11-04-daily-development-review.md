## A 判断：交互骨架成立，可靠执行仍待验证
当前设计适合继续验证单人、多 Agent 的开发流程。
专门对话、独立通知、并行任务与角色可选都值得保留。

目前还不能认定它已满足完整的日常开发需求。
正常路径比失败恢复、返修与交付路径更完整。
下一步应验证一次真实工作从启动到验收的全过程。

这次检查覆盖设计文档、说明页与原型代码。
原型使用内存和模拟回执，这是刻意选择。
下文区分原型缩写、设计缺口和真实接入要求。
本轮没有运行真实 Agent、CI 或故障注入。

## B 按日常开发场景检查覆盖情况
| 场景 | 当前覆盖 | 还需要什么 |
|---|---|---|
| 想法、澄清、Spec、拆任务 | Matt 流程已有文档 | 对话确认后能定位已保存的决策与任务 |
| 小修复、改文案、窄范围 bug | 有单会话概念 | 轻量入口，按任务需要展开角色 |
| 多任务并行与共同基线 | B 已演示 | 与 D 共享同一任务状态和集成证据 |
| 持续对话、后台通知 | D 已演示草稿隔离 | 长回复期间的新输入与事件排队 |
| 纠偏、补充约束 | 文档已有接收与落实链路 | 继续原 Agent、恢复失败、跨任务影响确认 |
| 直接查看代码、diff 与终端 | 原设计计划复用原生组件 | 绑定当前任务、worktree 和被审版本 |
| 人工验收与返修 | 文档已有结果包与版本规则 | 实际预览、行内反馈、返修后复验 |
| 合并、CI、交付 | 有 integration 与按需 PR | 明确本项目完成条件与外部状态来源 |
| 中断、隔夜、崩溃后恢复 | 有未知与陈旧原则 | 对账、恢复入口、重复请求处理 |
| 多项目与临时插单 | 有 effort 身份设计 | 每项目草稿、焦点和待处理项隔离 |

“文档已有”不等于原型已实现。
“原型已演示”也不证明跨进程操作可靠。

## C P0：统一工作状态与执行责任
早期设计定位为只读展示与人工入口。
后续设计加入暂停、恢复、调度和跨运行器交接。
这已经超出了单纯的布局需求。

应形成一份当前实施基线，明确三层职责。

| 层 | 负责 | 不应承担 |
|---|---|---|
| Herdr layout 与 mods | 显示、草稿、选中对象、证据入口 | 推测操作完成或重复启动任务 |
| 本地操作桥与持久记录 | 请求编号、投递回执、运行器连接、恢复对账 | 自行决定产品优先级 |
| 唯一 CoS／现有调度者 | 认领、依赖、执行协调与集成顺序 | 代替用户验收 |

操作桥是执行请求的通道，不增加第二个调度者。
采用 implement-spec 时，继续由它拥有调度权。
首版应约定一条真实的请求与回执路径。
尚未接通的能力只显示来源和人工操作入口。

本机 mod 的 exec 有 30 秒限制。
长期运行的 Agent 连接需要明确的生命周期承载位置。
不能把它隐含在 mod 重绘或一次短命令里。

依据：[早期范围与职责](./2026-11-04-matt-herdr-system-design.md)、[角色接入设计](./2026-11-04-agent-role-selection.md)。

本机接口依据：`~/.config/herdr-app/herdr.d.ts:10`。

B 与 D 当前分别维护自己的 workers、事件和运行状态。
D 启动 C 时直接假定依赖与共同基线已满足。
这是演练缩写，不能作为真实依赖放行的证明。

实现时，两种视图必须读取同一份状态。
切到任务图应看到刚在对话中发出的纠偏及其影响。

代码依据：`matt-workbench-prototype.html:69、126、144`。

## D P0：恢复能力决定它能否每天使用
| 日常故障 | 需要的行为 |
|---|---|
| UI 刷新或 mod 重载 | 恢复草稿、问题、请求编号和运行绑定 |
| 命令已执行但回执丢失 | 标记状态未知，先查询结果，再决定是否重试 |
| CoS 退出但 Worker 仍活着 | 显示实际进程与最后确认时间，避免重复启动 |
| 用户手动提交或修改文件 | 重新核对 head、dirty diff 和旧验证范围 |
| 额度不足或网络中断 | 保留现场，显示原因与可用恢复操作 |
| 验证失败或长期无进展 | 显示失败命令与最近进展，提供定向处理入口 |

操作记录至少关联 effort、ticket、run、request 和版本。
重试沿用请求身份，并由执行侧去重或核对。
每个工作项同时只允许一个有效执行认领。

关键状态不能只保留在对话 Agent 的记忆里。
对话恢复后，先从任务、版本与请求记录重建事实。
原型的“重置”不模拟这些恢复语义。

暂停要区分：Agent 轮次、子进程与外部操作。
中断轮次后，预览服务或测试进程仍可能运行。
界面需要明确已经停下什么，哪些状态仍未知。

原始通知、Agent 已读取和用户已处理分别记录。
Agent 汇总过一个问题，不代表用户已经回答。
重连时不能因此把未解决事项隐藏。

现有原则依据：[状态与恢复边界](./2026-11-04-matt-herdr-system-design.md)。

## E P0：补齐纠偏、验收和返修闭环
现有暂停演练适合解释回执区别。
但日常纠偏往往只需修正约束，再继续原 Agent。
当前 D 主要演示暂停后更换执行配置。
它还没有恢复原会话和重复纠偏的完整操作。

建议把一次纠偏展开为可追踪的过程。

```flow LR
纠偏请求 -> 确认对象与影响
确认对象与影响 -> 暂停受影响工作
暂停受影响工作 -> 更新依据与版本
更新依据与版本 -> Agent确认采用
Agent确认采用 -> 继续原会话或交接
继续原会话或交接 -> 返回修改证据
返回修改证据 -> 复核并关闭纠偏
```

跨任务改约定时，要核对已返回但尚未合入的提交。
旧依据上的结果应标记待复核，不能继续自动合入。
无关 Worker 可以继续执行。

人工验收在文档中已有正确规则。
下一步应把这些规则做成一个实际可用的结果面板。

| 验收材料 | 必须说明 |
|---|---|
| 代码与 diff | repo、worktree、base/head、未提交改动 |
| 运行预览 | 对应版本、入口、必要环境与测试数据 |
| 自动验证 | 命令、结果、输出和适用版本 |
| Standards / Spec review | 比较范围、发现、缺项与证据 |
| 用户反馈 | 对应画面或代码位置、预期与实际、阻塞性 |

用户可以明确通过、要求修改或暂缓。
返修后显示改了什么、旧结论哪里失效、需要复验什么。
只有实际需要人工判断的项目才设置人工 gate。

项目应预先约定完成条件。
完成可以要求本地验收、集成验证或 PR/CI 结果。
推送、发布和部署仍按本次任务授权执行。
不能统一用 Agent done 或已提交代替交付。

依据：[既有人机交互设计](./matt-human-interaction.html)、[原型暂停与交接](https://github.com/zengjie/herdr-matt-workbench/blob/prototype/unified-workspace/docs/design/matt-workbench-prototype.html?variant=D)。

## F P1：降低日常操作负担
| 改进 | 具体行为 | 对日常工作的价值 |
|---|---|---|
| 轻量任务路径 | 一个请求启动单 Worker；复杂后再拆分 | 小修复不必配置全部角色 |
| 附加上下文 | 对话中附文件、代码范围、截图和日志 | 用户能准确指出问题 |
| 当前对象标识 | 显示所讨论的 effort、ticket、run 与版本 | 选中项与指令对象不混淆 |
| 项目切换 | 保留各自草稿、打开的证据和未决问题 | 临时插单后可恢复主线 |
| 待办优先级 | 优先显示阻塞人的决策、验收与异常 | 通知多时仍知道先做什么 |
| 并行与资源控制 | 限制活跃 Worker；标记端口与环境占用 | 防止预览互相覆盖或任务失控 |
| 配置低频化 | 常用默认一键沿用，特殊任务再覆盖 | 模型选择不会成为每次启动的负担 |

配置页和讨论输入都应保留未保存内容。
当前原型重新打开配置或切作用域会重建编辑值。
正式交互应恢复分区草稿或明确显示放弃行为。

直接进入 Worker 对话时，显示当前接管对象。
产生共享约束后回写任务依据，并让 CoS 确认影响。
不要求所有局部交流再转述一遍。

证据变化可以自动更新状态，不自动抢占主屏。
只对新决策、实质阻塞与关键失败提高提示等级。

## G 布局收敛：一个工作区，三个阅读重点
D 的持续对话入口与 B 的全局任务视角都需要保留。
它们应属于同一工作区，并共享项目与任务绑定。

```tree
同一个 Effort
  顶部：目标、当前阶段、共同基线与状态更新时间
  左侧：项目导航与需要用户处理的事项
  主区：对话 / 任务图 / 结果与证据
  持续对话：主区切换时保留草稿与未完成轮次
  右侧：选中任务、操作回执与直接接管入口
  后台事件：独立收件箱，保留来源与处理状态
  角色与模型：低频配置入口
```

阅读日志、查看 diff 和验收时，需要足够大的主区。
持续对话可以收为底部输入区或可展开侧栏。
维持同一对话身份不要求聊天记录永久占满中央。

选中任务、正在讨论的对象和正在控制的运行分别表示。
发送前核对操作目标；切换阅读视图不改变执行对象。
保留直接进入终端的能力，前台不必转述全部细节。

## H 下一轮的验证顺序
建议保留现有原型为交互参考，再收敛实施基线。
真实接入先覆盖本机、单 repo、单 effort。

| 顺序 | 完整场景 | 通过条件 |
|---|---|---|
| 1 | 用对话启动一个小修复 | 真实目标绑定，能打开 diff 并核对验证结果 |
| 2 | A/B 并行，纠正 B 后继续原会话 | A 保留进度；B 采用新依据；旧结果不误合入 |
| 3 | UI 重启且一条回执丢失 | 恢复现场，不丢用户决策，不重复启动任务 |
| 4 | 发现问题、返修、复验与集成 | 验收对应实际版本，反馈可追踪到关闭 |
| 5 | 跨运行器交接 | 先确认暂停；新旧运行可追踪；关键依据完整 |

这些场景通过后，再扩展多项目与更大并行规模。

本次建议的优先级是：统一状态与责任、恢复、纠偏与验收。
轻量任务、上下文附件和布局收敛紧随其后。
模型默认组合继续作为可替换配置，等真实使用后再比较。
